Project 1: Automated Multi-Environment Deployment Pipeline 🔄

Difficulty: Beginner

Time to complete: 1–2 weekends

Skills demonstrated: CI/CD, Docker, GitHub Actions, environments

What you build:

A complete CI/CD pipeline for a web application that automatically:

  • Runs tests on every pull request
  • Builds a Docker image and pushes it to GitHub Container Registry
  • Deploys to staging automatically on merge to develop
  • Deploys to production on manual approval after merge to main

Architecture:

GitHub Push
    │
    ▼
GitHub Actions
    ├── Run tests (Jest/Pytest)
    ├── Build Docker image
    ├── Push to ghcr.io
    ├── Deploy to staging (automatic)
    └── Deploy to production (manual approval gate)

Tech stack:

  • GitHub Actions for the pipeline
  • Docker + GitHub Container Registry (ghcr.io) for images
  • Any simple web app (Node.js, Python Flask, Go) as the target
  • A VPS (Hetzner/DigitalOcean) or local VM as deployment target
  • SSH deployment or Docker Compose on the remote host

Key pipeline file:

# .github/workflows/deploy.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run tests
        run: npm ci && npm test
  
  build:
    needs: test
    runs-on: ubuntu-latest
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}
    steps:
      - uses: actions/checkout@v4
      - name: Log in to registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
          cache-from: type=registry,ref=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:cache
          cache-to: type=registry,ref=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:cache,mode=max
 
 deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/develop'
    environment: staging
    steps:
      - name: Deploy to staging
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.STAGING_HOST }}
          username: deploy
          key: ${{ secrets.STAGING_SSH_KEY }}
          script: |
            docker pull ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
            docker stop myapp || true
            docker run -d --name myapp --restart unless-stopped \\
              -p 3000:3000 \\
              ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}

  deploy-production:
    needs: build
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    environment: production   # Requires manual approval in GitHub settings
    steps:
      - name: Deploy to production
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.PROD_HOST }}
          username: deploy
          key: ${{ secrets.PROD_SSH_KEY }}
          script: |
            docker pull ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
            docker stop myapp || true
            docker run -d --name myapp --restart unless-stopped \\
              -p 3000:3000 \\
              ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}

What makes this resume-worthy:

  • Shows you understand environments and promotion gates, not just “push to deploy”
  • Demonstrates Docker image lifecycle management
  • Manual approval gate shows production deployment discipline

Starter repos to fork:

  • github.com/actions/starter-workflows
  • github.com/docker/build-push-action

# Updates the image tag in Git, ArgoCD picks up the change

A Backstage software template that creates new services:

# templates/new-microservice/template.yaml
apiVersion: scaffolder.backstage.io/v1beta3
kind: Template
metadata:
  name: nodejs-microservice
  title: Node.js Microservice
  description: Creates a new Node.js microservice with CI/CD, Dockerfile, and K8s manifests
spec:
  owner: platform-team
  type: service

parameters:
    - title: Service Details
      properties:
        name:
          title: Service Name
          type: string
          pattern: '^[a-z0-9-]+$'
        description:
          title: Description
          type: string
        owner:
          title: Team Owner
          type: string

  steps:
    - id: fetch-template
      name: Fetch Template
      action: fetch:template
      input:
        url: ./skeleton   # Your template files
        values:
          name: ${{ parameters.name }}
          owner: ${{ parameters.owner }}
    - id: create-repo
      name: Create GitHub Repository
      action: publish:github
      input:
        repoUrl: github.com?owner=myorg&repo=${{ parameters.name }}
        defaultBranch: main
    - id: register-catalog
      name: Register in Catalog
      action: catalog:register
      input:
        repoContentsUrl: ${{ steps['create-repo'].output.repoContentsUrl }}
        catalogInfoPath: /catalog-info.yaml

The key deliverable that makes this stand out:

The findings.md file, documenting what you hypothesized, what actually happened, and what you fixed. This demonstrates the complete engineering mindset: experiment, observe, improve.

## Experiment: Pod Kill — checkout-service
**Hypothesis:** Killing 50% of checkout pods will not affect service availability
because HPA will replace them within 60 seconds.

**What actually happened:**
- Service availability dropped to 78% for 90 seconds (not the expected 0% impact)
- Root cause: maxUnavailable was set to 1, but HPA minimum was 2. When we killed
  2 of 4 pods, the HPA took 90 seconds to provision new nodes via Karpenter.
- Readiness probe initialDelaySeconds was 60s - new pods weren't ready for 60+ seconds.

**Fixes applied:**
- Reduced readinessProbe.initialDelaySeconds from 60 to 15
- Added PodDisruptionBudget: minAvailable: 2
- Pre-scaled Karpenter NodePool to have warm capacity during business hours
**Result after fixes:** Same experiment passed with 99.2% availability maintained.

What makes this resume-worthy:

  • Almost no candidates have real chaos engineering experience in their portfolio
  • The hypothesis-result-improvement loop shows scientific engineering thinking
  • It demonstrates you operate systems, not just deploy them

Project 10: Custom Kubernetes Operator 🔧

Difficulty: Advanced-Expert

Time to complete: 1 month

Skills demonstrated: Go programming, Kubernetes internals, CRDs, controller pattern, operator pattern

What you build:

A real Kubernetes operator that extends the Kubernetes API with a custom resource. When you create a custom resource (e.g., a DatabaseBackup), your operator automatically takes the action and manages the lifecycle.

Example: A DatabaseBackup Operator

The custom resource your operator enables:

# Users of your operator create this resource
apiVersion: backup.mylab.io/v1alpha1
kind: DatabaseBackup
metadata:
  name: postgres-daily-backup
  namespace: production
spec:
  database:
    host: postgres-service
    port: 5432
    name: myapp_db
    credentialsSecret: postgres-credentials
  schedule: "0 2 * * *"       # 2 AM daily
  retention: 7                 # Keep 7 backups
  destination:
    type: s3
    bucket: my-backup-bucket
    region: us-east-1

The operator watches for this resource and:

  • Creates a CronJob that runs pg_dump on the specified schedule
  • Uploads the backup to S3
  • Deletes backups older than the retention period
  • Updates the DatabaseBackup status with last backup time and result

Bootstrap with Operator SDK:

# Install Operator SDK
brew install operator-sdk

# Create a new operator project
operator-sdk init \\
    --domain mylab.io \\
    --repo github.com/myorg/database-backup-operator

# Create the API and controller
operator-sdk create api \\
    --group backup \\
    --version v1alpha1 \\
    --kind DatabaseBackup \\
    --resource --controller

# This scaffolds:
# api/v1alpha1/databasebackup_types.go   → Define your CRD spec

# controllers/databasebackup_controller.go → Your reconcile logic

# Build and deploy
make docker-build docker-push IMG=ghcr.io/myorg/database-backup-operator:latest
make deploy IMG=ghcr.io/myorg/database-backup-operator:latest

The reconcile loop (the heart of every operator):

// controllers/databasebackup_controller.go
func (r *DatabaseBackupReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    log := log.FromContext(ctx)

    
    // Fetch the DatabaseBackup resource
    backup := &backupv1alpha1.DatabaseBackup{}
    if err := r.Get(ctx, req.NamespacedName, backup); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    // Check if a CronJob already exists for this backup
    cronJob := &batchv1.CronJob{}
    err := r.Get(ctx, types.NamespacedName{
        Name:      backup.Name + "-cronjob",
        Namespace: backup.Namespace,
    }, cronJob)

    if errors.IsNotFound(err) {
        // CronJob doesn't exist - create it
        newCronJob := r.buildCronJob(backup)
        if err := r.Create(ctx, newCronJob); err != nil {
            log.Error(err, "Failed to create CronJob")
            return ctrl.Result{}, err
        }
        log.Info("Created CronJob", "name", newCronJob.Name)
    } else if err != nil {
        return ctrl.Result{}, err
    } else {

        // CronJob exists - ensure it matches desired state
        r.updateCronJobIfNeeded(cronJob, backup)
    }

    // Update status
    backup.Status.LastScheduledTime = &metav1.Time{Time: time.Now()}
    if err := r.Status().Update(ctx, backup); err != nil {
        return ctrl.Result{}, err
    }
    return ctrl.Result{RequeueAfter: time.Minute * 5}, nil
}

What makes this resume-worthy:

  • Operator development is one of the most rare and valued Kubernetes skills, very few engineers at any level have done it
  • Demonstrates Go programming ability alongside Kubernetes expertise
  • Shows you understand Kubernetes internals, not just how to use kubectl
  • Custom operators are how platforms extend Kubernetes for their specific needs, exactly what Platform Engineering teams do

Starter repos:

  • github.com/operator-framework/operator-sdk
  • github.com/kubernetes-sigs/kubebuilder
  • github.com/operator-framework/awesome-operators real operators to study

🗺️ Final Thoughts

  • None of these projects is complete the moment you get it running.
  • The real learning comes from breaking it, rebuilding it with better architecture, adding a feature you didn’t plan for, and writing down what you learned.
